# ADR-0032: Frontend ESLint 10 flat config with frozen Airbnb values

**Date**: 2026-10-01
**Status**: accepted
**Deciders**: Gasper Grom, reviewed by @themarolt and @joanagmaia in #4859

## Context

The frontend linted with an `.eslintrc.js` on ESLint 8, `@vue/eslint-config-airbnb` 7, `eslint-plugin-vue` 9 and `@typescript-eslint` 5. ESLint 8 is out of support, and `@vue/eslint-config-airbnb` has no release for ESLint 9 or later. ADR-0031 keeps ESLint on the frontend because oxlint has no Vue template rules. The migration must not change which findings the code reports, so that later rule tickets (CM-1518) start from a known baseline.

## Decision

Replace `.eslintrc.js` and `.eslintignore` with `frontend/eslint.config.mjs` on ESLint 10, `eslint-plugin-vue` 10 and `typescript-eslint` 8, wired through `@vue/eslint-config-typescript`. The Airbnb rule values are frozen in `frontend/.eslint/airbnb-rules.json` instead of depending on a package. The rest of the setup is:

- `eslint-plugin-import-x` is registered under the name `import`, so existing rule ids and `eslint-disable` directives keep working. A small wrapper removes the autofix of `import/no-duplicates`, because the fixer in import-x 4.17.1 merges value imports into `import type` and erases them.
- Prettier's rule overrides apply to `.js`, `.ts`, `.mjs` and `.cjs` only. `.vue` files keep the formatting rules that `eslint-config-prettier` would switch off, since Prettier does not format them.
- `@typescript-eslint/consistent-type-imports` lives outside `withVueTs`. Inside it, the rule turns on type-aware parsing for every file and lint takes about 2.5 times longer.
- `frontend/.eslint/legacy-files.json`, regenerated by `scripts/eslint-legacy-files.mjs`, lists the files that still violate a ratchet rule (`vue/component-api-style`, `vue/block-lang`, `vue/prefer-define-options`). Each list becomes an override that turns the rule off for those files, so new files must comply.
- Rules that the new presets enable but the old setup did not stay off until a ticket turns them on. After review only `vue/no-required-prop-with-default` stayed off in CM-1517; CM-1518 enabled it together with five more Vue rules, one rule per pull request.
- `reportUnusedDisableDirectives` is off, because ESLint 9 and later default it to a warning and lint runs with `--max-warnings=0`.

## Alternatives Considered

### Alternative 1: `eslint-config-airbnb-extended`

- **Pros**: A maintained flat-config port of Airbnb.
- **Cons**: A new dependency with its own rule changes, so the set of reported findings would move at the same time as the ESLint upgrade.
- **Why not**: The goal was parity first. A port can be adopted later as a separate, reviewable change.

### Alternative 2: Drop Airbnb and keep only the Vue and TypeScript presets

- **Pros**: Fewer rules and no frozen JSON file.
- **Cons**: The set of violations changes, and the repo would need a clean-up pass in the same PR.
- **Why not**: It mixes a tooling upgrade with a policy change. It can still be done on top of this config.

### Alternative 3: oxlint for the frontend

- **Why not**: Rejected in ADR-0031: no `eslint-plugin-vue` template rules.

## Consequences

### Positive

- ESLint 10 and current plugins, a single `eslint.config.mjs`, and lint at 0 warnings with `--max-warnings=0`.
- Existing rule ids, disable directives and ratchet lists keep working.
- Stricter Vue rules can be enabled one at a time.

### Negative

- `.eslint/airbnb-rules.json` is edited by hand from now on. Nothing updates it.
- The `no-duplicates` wrapper depends on import-x internals.
- The react, `jsx-a11y` and `vuejs-accessibility` rules that Airbnb enabled are gone. There is no JSX in the frontend, and CM-1746 re-adds the accessibility rules with a ratchet.

### Risks

- Upgrading import-x can break the wrapper. Revisit it, and delete it if the upstream fixer is correct.
- Plugin presets add new rules in every major release. Compare `eslint --print-config` before and after an upgrade and keep new rules off until a ticket enables them.
